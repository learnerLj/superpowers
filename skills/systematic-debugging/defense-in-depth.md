# 纵深防御

## 核心原则

纵深防御是在不同信任边界承担不同保护职责，不是在每层复制同一业务规则。

每项业务不变量必须有唯一 owner 和 canonical representation。其它层引用该事实或消费已经验证的类型，不得各自维护一份可能漂移的判断逻辑。

## 保护位置

### 1. 不可信输入边界

解析外部输入并拒绝格式错误、缺失字段、非法范围或无法识别的 identity。成功后尽早转换为携带不变量的 canonical type。

### 2. 唯一事实所有者（Canonical owner）

唯一 owner 定义并执行真正的业务不变量。只有合法 writer 能创建或改变该状态；其它组件不能重新推导同一事实。

### 3. 跨组件转换边界

只验证当前转换的 contract，例如 schema 版本、单位、编码、字段裁剪和 identity 对应关系。这里不复制业务规则；转换后的 projection 也不能成为第二个 authority。

### 4. 不可逆或高风险副作用之前

发送交易、写入持久化状态、删除数据或调用外部系统前，检查当前操作所需的前置条件和目标身份。这是操作保护，不是重新实现 canonical owner 的全部校验。

### 5. 可观测性

记录足以定位失败边界的结构化上下文。日志提供证据，不参与业务判断，也不能成为状态副本。

## 设计检查

为每个拟增加的检查回答：

| 问题 | 合格答案 |
|---|---|
| 谁拥有这项不变量？ | 一个明确的结构或组件 |
| 本层为何还要检查？ | 它承担不同的信任边界或副作用职责 |
| 本层检查什么？ | 只检查本层 contract，不复制业务规则 |
| 失败如何表达？ | 使用本层可行动的错误，并保留根因上下文 |
| 如何防止漂移？ | 复用 canonical type、共享 value object 或显式引用 owner |

如果两个位置逐字段执行同一判断，应合并到唯一 owner，或提取共享的 canonical type；“多一层更安全”不能证明重复规则合理。

## 验证

- 测试 canonical owner 的不变量和合法 writer；
- 测试每个信任边界只拒绝它负责的非法输入；
- 测试 projection 或转换不能绕过 canonical owner 写入业务状态；
- 测试高风险操作在身份或前置状态不满足时停止；
- 验证日志足以定位失败，但不包含敏感信息。

纵深防御的结果应是一个事实来源和多个职责不同的保护边界，而不是多个互相竞争的事实副本。
