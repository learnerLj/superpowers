# 系统化调试

## 概述

系统化调试拥有从异常现象到根因证据的调查方法。它不以“尽快改点什么”为目标，而是先回答：问题在哪里发生、为什么发生、证据能排除什么，以及是否真的需要修改软件。

**核心原则：** 尝试修复前，必须先用证据确认根因；只修症状就是失败。

```text
没有根因证据，就不把任何变更称为根因修复
```

## 任务边界

- 用户只要求诊断、分析或报告原因时，完成诊断结论后停止，不修改代码、配置或外部状态。
- 用户已经要求修复时，也必须先完成根因调查；确认需要改变软件行为后，修复切片使用 `test-driven-development`。
- 用户或项目 authority 明确授权紧急止损、回滚或隔离时，可以在根因确认前执行独立的缓解动作；先保留安全范围内的现场证据，只做范围受限、可回退且能直接验证风险下降的变更。缓解不是根因修复，执行后继续调查，不能声称根因已修复。
- 长时间 debugging 由 `brainstorming` 创建唯一 mixed-profile spec；本 skill 只拥有诊断方法，不创建第二份计划或进度记录。
- 调查证明问题来自环境、外部系统或操作状态，而且无需修改软件时，以证据结束，不虚构实现任务。

## 四个阶段

必须完成当前阶段的成功标准，才能进入下一调查阶段。如果所有当前已获授权且安全可得的证据已经穷尽，可以从任一调查阶段直接进入阶段 4 交付未确认诊断；这条退出路径不能进入软件修复。

### 阶段 1：建立事实与定位边界

1. **完整读取失败信息**：保留精确错误、stack trace、时间、路径、错误码和相关上下文。
2. **建立最小复现**：记录输入、步骤、环境和频率；无法稳定复现时，明确标记并继续收集证据。
3. **检查变化**：查看相关 diff、近期提交、依赖、配置、部署和环境差异。
4. **观察组件边界**：记录进入和离开边界的数据、配置与状态，运行一次以定位最先偏离预期的位置。
5. **反向追踪数据流**：从坏值或失败动作逐层追问构造方、writer 和上游 owner，直到最初触发点。复杂调用链使用 `root-cause-tracing.md`。

成功标准：能够说明异常最早在哪个边界出现，并给出可定位的复现或观测证据。若仍无法定位，继续调查，不进入修复。

### 阶段 2：对照正常路径

1. 在同一系统中找到最接近的正常路径。
2. 确认真实 owner、运行时入口、配置来源、消费方和相关 authority。
3. 比较正常与异常路径的输入、状态、依赖、顺序和环境，列出有证据的差异。
4. 区分相关性与因果性，不因某项差异看起来很小就提前排除，也不把所有差异都当成根因。

成功标准：形成有限的差异集合，并能解释每项差异如何支持或反驳后续假设。

### 阶段 3：提出并检验假设

1. 一次只写一个可证伪假设：`我认为 X 是根因，因为 Y；若成立，应观察到 Z。`
2. 设计只改变一个变量的最小诊断实验。诊断观测、临时日志和只读查询不是生产修复。
3. 记录实验输入、结果以及它支持或推翻了什么。
4. 假设被推翻后回到阶段 1 或提出新假设；不能在失败修复上继续叠加变更。
5. 证据不足时明确写 `根因尚未确认`，不要用确定语气补齐未知部分。

成功标准：根因得到直接证据或排他性证据支持，且能解释已观察到的症状。未达到该标准但证据已经穷尽时，使用四阶段开头的未确认退出路径。

### 阶段 4：形成诊断结论并交接

诊断结论必须包含：

- **症状与影响**：实际发生了什么，影响到哪些消费方；
- **复现与边界**：如何复现，在哪些环境或输入下发生；
- **证据链**：从症状到最初触发点的可定位证据；
- **已排除项**：检验过但不成立的假设；
- **根因状态**：`已确认`、`最受证据支持但未确认` 或 `尚未确认`；
- **Owner 与失败边界**：哪个组件拥有相关事实，最早在哪个边界偏离；
- **变更判断**：是否需要代码、配置、外部状态或无需变更；
- **剩余未知与下一步**：还缺什么证据，或应进入哪个执行流程。

根据用户授权交接：

- **只要求诊断**：提交上述结论并等待，不提出顺手修改。
- **已授权紧急缓解**：把止损、回滚或隔离作为独立状态变更执行并验证，明确记录它没有证明根因；若缓解需要修改实现代码、parser、默认值、校验或其它软件 contract，仍使用 `test-driven-development`，除非用户明确授权其例外。
- **已授权修复且需要软件变更**：使用 `test-driven-development`，以能复现已确认根因的失败回归测试开始一个根因修复。
- **只需配置或外部状态变更**：按项目 authority 和用户授权执行，并用变更前后状态证明结果。
- **复杂、高风险、跨组件或公共 contract 修复**：完成实现后使用 `requesting-code-review`；reviewer 返回 findings 时使用 `receiving-code-review`，按授权边界处理后使用 `verification-before-completion`。
- **所有路径**：声明诊断、修复或状态变更完成前，使用 `verification-before-completion` 检查对应证据。

## 防止修复变成新的问题

确认根因后，如需增加保护，使用 `defense-in-depth.md`。纵深防御不等于复制业务规则：不变量必须有唯一 owner，其它层只在自身信任边界承担不同职责的检查。

异步或不稳定测试使用任意 `sleep`、固定 timeout 猜测时序时，阅读 `condition-based-waiting.md`。

## 多次失败时

分别统计：

- **被证伪的诊断假设**：说明调查仍在收敛，不自动证明架构错误；
- **已经实施但失败的修复**：说明当前根因判断或系统边界可能有问题。

如果已经实施 3 次修复仍未解决，停止继续试改，汇总每次修复及新证据，与人类伙伴复核根因、共享状态、耦合和架构假设。这个门槛触发的是架构审查，不是“架构已经被证明错误”。

## 必须停下并回到调查的信号

- “先改一下看看”；
- 同时改变多个变量；
- 未复现、未定位就列修复方案；
- 把日志出现的位置直接当作根因位置；
- 为了赶时间跳过证据；
- 根因尚未确认，却使用确定语气；
- 用户只要求诊断，却开始修改；
- 一个失败修复上继续叠加另一个修复。

## 常见借口

| 借口 | 事实 |
|---|---|
| “问题很简单” | 简单症状也可能由上游状态造成；最小调查通常很快。 |
| “先修再证明” | 修改会污染现场，使后续因果判断更困难。 |
| “这个差异最可疑” | 可疑只产生假设，实验才能产生证据。 |
| “多改几处更容易成功” | 多变量变更无法判断哪一项有效。 |
| “三次假设失败说明架构错了” | 被证伪的假设不是失败修复；先继续收敛证据。 |
| “每层都复制校验最安全” | 重复业务规则会漂移；唯一 owner 与边界职责更安全。 |
| “反正修复可回滚” | 可回滚不等于已获修改授权。 |

## 快速参考

| 阶段 | 核心动作 | 完成证据 |
|---|---|---|
| 1. 事实与边界 | 读错误、复现、查变化、追踪数据 | 找到最早异常边界 |
| 2. 正常路径 | 找 owner、authority 和可用对照 | 得到有限差异集合 |
| 3. 假设检验 | 单一假设、单一变量、记录结果 | 根因被支持或明确未确认 |
| 4. 结论与交接 | 输出诊断 contract，按授权路由 | 诊断结束或进入适用执行流程 |

## 配套方法

- `root-cause-tracing.md`：沿调用与数据流反向追踪最初触发点；
- `defense-in-depth.md`：在不复制 SSOT 的前提下设置边界保护；
- `condition-based-waiting.md`：用可观察条件替代任意延迟。
