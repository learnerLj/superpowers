# 根因追踪

## 核心原则

错误经常在调用链深处显现。不要停在抛错位置；从坏值、错误状态或危险动作开始，沿构造方、writer 和调用方反向追踪，直到找到最初触发点。

## 追踪步骤

1. **固定症状**：记录精确错误、坏值、失败动作和所在边界。
2. **找到直接原因**：说明当前函数为什么会产生该结果。
3. **继续追问来源**：谁调用它、谁构造参数、谁最后写入状态？
4. **定位 canonical owner**：哪个结构、配置或组件真正拥有这项事实？
5. **找到最初偏离**：在哪个 writer 或转换边界，正确状态第一次变成错误状态？
6. **建立证据链**：每一步都引用可定位的日志、调用点、状态快照或复现结果。

```text
症状
  <- 直接失败动作
  <- 收到错误输入或状态
  <- 上游转换或 writer
  <- canonical owner 最初产生错误事实
```

## 无法继续追踪时

先判断增加观测是否需要修改代码、配置或外部状态。需要修改时先取得授权；用户只授权诊断时，只记录缺少的观测和建议位置，不自行添加。

获得相应授权后，在信息丢失之前增加最小诊断观测，记录：

- 输入与输出；
- identity、时间和环境；
- 调用栈或 correlation ID；
- 配置来源与实际值；
- 状态变更前后的值。

观测应放在疑似失败边界之前，并避免记录 secret、私钥、完整凭据或不必要的个人数据。取得证据且获得清理授权后，删除临时噪声；确有长期价值的观测只有经过正常实现与验证流程，才能纳入正式可观测性 contract。

## 成功标准

根因追踪完成时，应能用一条连续证据链回答：错误事实由谁最先产生、经过哪些边界、为什么直到下游才暴露。只能解释最后一次报错，不算找到根因。
