# 处理审查反馈

先对照需求、真实代码和消费路径核查 finding，不把 reviewer 的判断当成事实或新增需求。

- 记录问题、依据和处理状态；多轮复查沿用稳定 ID，不要求固定 ledger 字段。
- 意见正确且属于已授权实现范围时直接修复，验证受影响行为，再请原 reviewer 定点复查。
- 意见错误时用代码或事实说明；证据不足时说明缺什么，不为了让审查通过而迎合建议。
- 含糊问题只阻塞依赖它的工作，明确且独立的已授权修复可以继续。按风险和依赖安排修复，相关问题可以合并验证。
- 用户只要求审查时交付核查结果；新增目标或超出授权的副作用先解决范围问题。已有实现授权不因收到反馈而失效。

确认的阻塞问题处理完并完成必要复查后，进入 `verification-before-completion`。无法解决的问题如实保留，不换 reviewer 或 ID 掩盖它，也不把局部通过说成整体完成。
