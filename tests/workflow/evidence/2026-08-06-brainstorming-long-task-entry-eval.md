# Brainstorming 长任务入口合并评估

## 证据边界

- 目标：验证删除独立 `using-superpowers` 后，显式调用 `brainstorming` 仍覆盖短任务退出、长期研究、spec 恢复和长期 debugging。
- Control：`tests/workflow/evidence/2026-08-06-general-long-task-routing-evals.md`，旧入口 hash `38bbc5945ac6f0e9186820da72f6b802b8098ed0afbd63b21bbf1dc767168c89`。
- Candidate：`skills/brainstorming/SKILL.md`，SHA-256 `347ba18a2cbf6678110e6a24575db2fc3d9c904601c96ddb0296a4601ce517a6`。
- 方法：5 个 fresh-context 只读 evaluator；每个 evaluator 先完整读取 candidate，再直接回应任务；不得编辑、实现或提交。
- 限制：本轮验证显式 `$brainstorming` 调用后的路由与输出，不证明任一 harness 的 implicit invocation 命中率。

## 样本 1：手动长期分析

### Prompt

> `$brainstorming 我想系统分析我们是否应该把一套长期研究流程从本地笔记迁移到数据库。我需要一份能跨多次会话继续执行的 spec，先不要实际迁移。`

### Raw response

> 我会用 `brainstorming` 把它整理成一份中文的、可跨会话恢复的 executable spec。这个 spec 会先回答“是否值得迁移”，不会预设数据库一定更好，也不会执行建库、导入或修改笔记。
>
> 分析会明确比较三条路线：继续以本地笔记为主、笔记与数据库混合、数据库成为主 authority。判断依据至少包括查询与关联能力、写作体验、版本历史、可移植性、自动化需求、数据一致性、维护成本、备份恢复和供应商锁定。每个结论会区分已验证事实、推断、`NOT VERIFIED` 和待验证项，并通过小规模可逆验证来支持最终决策。
>
> 为了让 spec 足够具体且能由下一次会话直接接续，我先需要一个会实质改变范围的信息：这套“长期研究流程”目前具体位于哪里？请给我本地笔记根目录或入口索引路径，并简单说明一次典型流程，例如“收集资料 -> 摘录 -> 建立实体关系 -> 分析 -> 输出报告”。
>
> 如果已经有倾向的数据库，也请一并说明；如果没有，我会把 SQLite/DuckDB、PostgreSQL 和保持文件型存储作为候选，而不是提前替你选定。拿到入口后，我会先只读盘点现状、查找是否已有同目标 spec，再生成唯一的长期执行 spec，交给你审阅；在你明确批准迁移前不会进入实际迁移 slice。

判定：PASS。直接进入长期 spec 流程，没有依赖其它路由 skill，也没有提前执行迁移。

## 样本 3：长期研究

### Prompt

> `$brainstorming 我准备做一个持续两周、需要查多个官方来源的监管政策研究。先帮我建立执行约束，研究结论必须区分事实、推断和未验证项。`

### Raw response

> 这是一个长周期 Research Evidence 任务。我会先建立并固化一份 executable spec，在目标、法域、authority、交付物、执行 slice、完成证据和修订条件明确前，不开始检索，也不提前形成政策判断。
>
> 先锁定以下执行约束：
>
> - **来源边界**：核心事实只以一手官方来源为 authority，包括现行法规原文、政府公报、监管机构正式公告、官方 FAQ/指引、执法决定和司法文书。新闻、律所解读、行业文章只能作为线索或解释材料，不能单独证明监管事实。
> - **来源优先级**：法规或正式决定原文 > 发布或执行该规则的主管机关文件 > 其它政府机构材料 > 官方讲话、咨询稿和 FAQ。咨询稿、提案、讲话不得表述成已生效规则。
> - **时点约束**：每项政策事实必须记录适用法域、发布日、生效日、截至研究截止日的有效状态，以及是否存在修订、废止、过渡期或地区差异。
> - **可追溯性**：每个关键结论必须能回到具体官方页面或文件、发布日期、条款或页码、访问日期。仅有搜索摘要、二手转述或失效链接不算完成证据。
> - **结论标签**：
>   - `事实`：官方来源直接支持，且表述不超出原文覆盖范围。
>   - `推断`：由一个或多个已验证事实推导；必须单列推理链、前提和可能的替代解释。
>   - `NOT VERIFIED`：只有线索、缺少原文、来源冲突尚未解决，或无法确认当前有效性。
>   - `未解决不确定性`：明确说明缺少什么证据、为什么两周内无法消除，以及它会影响哪些结论。
> - **交叉印证**：高影响结论原则上要求法规原文与主管机关执行材料相互印证。若只能找到一个官方来源，要明确标注单一来源边界，不能用重复转载冒充独立印证。
> - **冲突处理**：来源矛盾时不做静默合并；记录冲突文本、authority 层级、时间顺序和适用范围。无法解决时保持 `NOT VERIFIED`。
> - **禁止事项**：不把政策目标当成实际执行效果，不把个案执法自动推广为普遍规则，不把缺少禁止条款解释为许可，也不把仍在征求意见的内容写成最终政策。
> - **范围控制**：两周内先完成约定的核心问题和法域；发现相邻议题只进入待研究清单，除非新事实会推翻现有范围或结论，才触发 spec 修订。
> - **进度与证据**：按“范围与问题矩阵 -> 官方来源清单 -> 条款级提取 -> 交叉比较与反证 -> 综合结论 -> 新鲜证据复核”推进。每个 slice 只有在证据可定位后才能标记完成。
> - **最终验收**：结论表中的每条陈述都有标签和来源；所有链接与有效状态在交付前重新检查；事实与推断没有混写；`NOT VERIFIED` 项没有被纳入确定性摘要；报告明确覆盖边界、遗漏项和截止日期。
> - **修订条件**：法域、研究对象、时间窗口、最终读者或交付形式变化，或者出现会改变 authority 排序的新法规、正式修订或司法决定时，先修订 spec，再继续研究。
>
> 现在还缺一个会实质改变执行范围的信息：请给我这次研究的**政策主题、法域、截止时点和最终交付物**。例如：“欧盟与美国的加密稳定币监管，截至 2026-08-20，交付一份供交易业务决策使用的中文对比报告”。我会据此把上述约束写成完整、可恢复执行的两周研究 spec，再进入官方来源检索。

判定：PASS。使用 research evidence，没有把人工研究误归为 TDD。

## 样本 4：恢复已有 Spec

### Prompt

> `$brainstorming 我们昨天已经有一份执行到第三个 slice 的长期分析 spec。今天继续，但其中两个数据源已经更新。你会怎么恢复？`

### Raw response

> 我不会直接从第四个 slice 接着跑。两个数据源更新后，正确恢复点取决于它们影响了哪些输入、产物和证据；必要时要重新打开前面已完成的 slice。
>
> 我会这样恢复：
>
> 1. 重新读取用户指令、项目 authority 和昨天那份 spec，确认它仍然拥有同一个目标；继续维护原 spec，不另建计划或进度表。
> 2. 核对前三个 slice 的实际交付物和可定位证据，不仅相信勾选状态或对话记忆。
> 3. 为两个更新源记录当前版本、时间范围、获取时间、schema/语义变化及 provenance，并与昨日使用的版本比较。
> 4. 沿 spec 的依赖关系做影响分析：
>    - 仅新增数据：重跑依赖该时间范围的收集、提取、比较和综合。
>    - schema 或语义变化：先修订输入 contract、方法和完成证据。
>    - authority 变化：视为实质性 spec 变化，停止执行并重新审查。
> 5. 重新打开所有输入、产物或完成证据已过期的 slice；不受影响且证据仍有效的 slice 保持完成。
> 6. 从最早一个“依赖已重新满足”的 slice 恢复，而不是机械地从第三或第四个 slice 开始。
> 7. 更新后的结果如果改变目标、交付物、证据 profile、风险边界、验收标准或 slice 结果，先修改同一份 spec；若属于需要批准的软件行为变更，则重新取得批准后再继续。
> 8. 最终验收时使用两个数据源的当前版本重新验证所有结论，并明确标注已验证事实、推断、`NOT VERIFIED` 和遗留不确定性。
>
> 恢复后的 spec 会明确写出：昨日恢复位置、两个来源的新旧版本、受影响的 slice、重开原因、仍有效的证据，以及下一个可执行 slice。
>
> 实际开始时，我先定位并读取那份 spec，再识别两个更新的数据源和版本差异；这三项足以决定真实恢复点。

判定：PASS。恢复原 spec，不创建第二份执行大纲，并正确处理过期证据。

## 样本 5：长期 Debugging

### Prompt

> `$brainstorming 一个间歇性线上故障可能要排查几天，现在还不知道是否需要改代码。请先建立可以跨会话恢复的执行方式。`

### Raw response

> 我会把它按“长时间 debugging”建立为可恢复任务：用一份中文 mixed-profile executable spec 作为唯一执行台账，不另建 plan、TODO 或第二份调查记录。
>
> 这份 spec 会持续保存：
>
> - 故障现象、影响范围、目标与明确非目标
> - 生产环境的只读边界、允许副作用和受保护状态
> - runtime authority、日志/指标/配置入口及当前证据
> - 已知事实、未知项、候选假设、复现条件和已排除假设
> - 按依赖排列的调查 slice、当前恢复位置和每步完成证据
> - 根因结论的证据门槛、反证以及 `NOT VERIFIED` 项
> - 哪些新事实会使调查方向或 spec 失效并触发修订
> - 最终验收时必须重新采集的新鲜证据
>
> 诊断阶段使用 research evidence 和 systematic debugging，只做观测、复现、缩小边界与验证假设，不预设一定需要改代码。只有证据明确指向软件缺陷时，才修订同一份 spec，加入 behavior-evidence 修复 slice、测试映射、回滚方式和实现审批门槛；若证据表明无需改代码，则以根因报告和运行状态证据结束。
>
> 以后任何新会话都先重新读取用户要求、项目 authority 和这份 spec，再核验已声明的产物与证据是否仍有效；过期的 slice 会重新打开，然后从下一个依赖已满足的 slice 继续。第一步应先检查仓库里是否已经存在同目标 spec，避免产生两套 authority。

判定：PASS。诊断与修复 profile 分离，只有确认需要修复时才进入 TDD。

Candidate 在本轮 5 个显式调用样本中保持了旧 workflow 的关键行为，并去掉了独立路由 skill。隐式触发率未在本轮验证，不能据此声称 Claude Code 或 Codex 一定会自动加载 `brainstorming`。
